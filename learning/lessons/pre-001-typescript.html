TypeScript 核心：PI 里用到的那些类型模式

约 15 分钟 · 只讲 PI 代码里真实出现的 TS 模式 · 目标：读 PI 源码时不再被类型签名绊住

这一课结束你会得到：看到 AgentTool<any>、message.content.filter(c => c.type === "toolCall")、satisfies Model<any> 时，能立刻说出它们在做什么。

0. 一句话理解 TypeScript

TypeScript = JavaScript + 类型标注。类型只在编译时起作用（erasable，擦除后就是纯 JS），运行时不存在。它的核心价值是：编译器帮你在跑之前抓住"用错了"的错误。PI 是 100% TS，所以源码里到处都是类型。

1. 接口 interface：描述对象长什么样

PI 用 interface 描述配置对象。来自 packages/agent/src/agent.ts：

export interface AgentOptions {
  initialState?: Partial<...>;
  convertToLlm?: (messages: AgentMessage[]) => Message[];
  streamFn: StreamFn;
  getApiKey?: (provider: string) => Promise<string | undefined> | string | undefined;
  beforeToolCall?: (ctx, signal?) => Promise<BeforeToolCallResult | undefined>;
}

三个要点：

  • ?: 表示可选属性——可以不传
  • 函数类型写作 (参数) => 返回值
  • Promise<X> 表示这个函数是异步的，返回一个最终值为 X 的 Promise

2. 泛型 Generics："类型也是参数"

PI 大量用泛型。最直观的例子是工具定义：

export interface AgentTool<TArgs> {
  name: string;
  execute(toolCallId: string, args: TArgs, ...): Promise<AgentToolResult<any>>;
}

AgentTool<TArgs> 里的 TArgs 是"类型参数"——不同工具的 args 不同（read 工具的参数是 { path: string }，bash 是 { command: string }），用泛型就能用一个 interface 描述所有工具，同时每个工具的参数类型是精确的。

同理 EventStream<TEvent, TResult>、Model<TApi>、Context，都是泛型容器。读代码时看到 <T>，把它当成"留空的类型，用的时候再填"。

3. 联合类型与可辨识联合：PI 消息系统的骨架

PI 的消息是可辨识联合（discriminated union）——多个对象类型共享一个"判别字段"（通常是 type 或 role），用来区分自己是哪一种。来自 agent-loop.ts：

const toolCalls = message.content.filter((c) => c.type === "toolCall");

message.content 是一个联合数组，元素可能是 { type: "text", text }、{ type: "toolCall", name, arguments } 等。c.type === "toolCall" 这个判断同时做了两件事：

  1. 运行时：筛出真的是 toolCall 的项
  2. 类型收窄：在 filter 之后，TypeScript 知道剩下的元素一定是 toolCall 类型，可以安全访问 .name、.arguments

这是 PI 里最常见的模式，几乎每个事件/消息类型都靠它。

4. 类型守卫 type guard：把"可能是"变成"就是"

类型守卫是一个返回 x is Y 的函数，告诉 TS"如果我返回 true，那 x 就是 Y"。PI 里最典型的是 validateToolArguments，但更简单的例子是用 instanceof：

catch (error) {
  return createErrorToolResult(
    error instanceof Error ? error.message : String(error)
  );
}

error instanceof Error 是内置类型守卫：成立时，TS 允许访问 error.message；不成立时走 String(error) 兜底。

5. satisfies 运算符：PI 里很常见的"既要又要"

来自 agent.ts：

const DEFAULT_MODEL = {
  id: "unknown",
  name: "unknown",
  api: "unknown",
  ...
} satisfies Model<any>;

satisfies 的意思是：检查这个对象值是否符合 Model<any> 类型，但保留对象自身的字面量类型。和直接写 : Model<any> 的区别是：

  • const x: Model<any> = {...} —— x 的类型被"抹平"成 Model，丢失了具体字段
  • const x = {...} satisfies Model<any> —— 既校验了形状，又保留了 id: "unknown" 这种字面量信息

PI 用它来定义默认值，既保证类型对，又能在后续做精确匹配。

6. 可选链与空值合并：写得少，错得少

PI 里到处是 ?. 和 ??：

const tool = currentContext.tools?.find((t) => t.name === toolCall.name);
if (!tool) { return { kind: "immediate", result: createErrorToolResult(`Tool ${toolCall.name} not found`), isError: true }; }
  • tools?.find(...)：如果 tools 是 undefined，直接返回 undefined，不报错
  • ??（空值合并）：a ?? b 当 a 是 null/undefined 时取 b，否则取 a（注意 0 和 "" 不算空）

7. as 断言：告诉编译器"我知道得更多"

const result = await prepared.tool.execute(
  prepared.toolCall.id,
  prepared.args as never,
  signal,
  ...
);

as never / as X 是类型断言：告诉 TS"别管你推断的，按我说的类型来"。它不做运行时检查，用错了还是会崩。PI 用 as never 是因为泛型工具的 args 类型在运行时统一调度，类型层面做不到精确匹配。初学者记住：能用类型守卫解决就别用 as。
