一次输入怎么变成一次模型调用

约 12 分钟 · 建立在 Lesson 1 仓库地图 之上 · 目标：口述完整的"输入 → 模型调用 → 输出"链路，并能在仓库里指出每一步

这一课结束你会得到：一条可以讲给别人听的完整数据流——用户在终端敲下一句话，到模型跑完、回复渲染出来，中间经过 4 个环节；以及每个环节对应的真实代码位置。

1. 全景：一条 4 段式链路

  1. 输入：用户在 TUI 里回车，输入被 session.prompt() 收走（interactive-mode.ts）
  2. 会话：AgentSession 把它转成消息，交给 pi-agent-core 的 Agent.prompt()
  3. 主循环：runAgentLoop 启动，streamAssistantResponse 负责"问模型一次"
  4. 模型调用：streamFunction（默认 streamSimple）按模型路由到对应供应商，发 HTTP/SSE 请求

2. 第 1 段：从键盘到会话

交互模式里，用户输入在 interactive-mode.ts 的 onPrompt 处理中被收集，最终调用 this.session.prompt(userInput)（interactive-mode.ts 约 1135 行）。AgentSession（core/agent-session.ts）做一两层封装后，第 1108 行执行 this.agent.prompt(messages)——至此控制权离开 coding-agent，进入 pi-agent-core。

在 Agent.prompt()（agent.ts）里，字符串被 normalizePromptInput 包成一条 user 消息：{ role: "user", content: [{ type: "text", text: "..." }], timestamp }。

3. 第 2 段：主循环开转

runAgentLoop()（agent-loop.ts 96 行）把 prompt 追加进上下文，开始发声事件，然后进入 runLoop()（156 行）。主循环由内层循环（一轮轮的模型调用）和外层循环（检查是否还有其他排队消息）组成。所有变化都以事件广播出去：agent_start → turn_start → message_start/message_update/message_end → turn_end → agent_end。TUI 就是订阅这些事件来画屏幕的。

内层循环的"燃料"只有一样东西：上下文。每一次模型调用都带上完整历史；工具结果也只是追加进历史里的普通消息，然后让模型再看一次。

4. 第 3 段：模型调用的边界

每次"问模型"发生在 streamAssistantResponse()（agent-loop.ts 279 行），顺序是：

  1. transformContext(messages)（可选）——比如长对话压缩（compaction）在这里发生，仍是 AgentMessage[]。
  2. convertToLlm(messages)——关键的翻译边界：把 AgentMessage[] 转成 LLM 能吃的 Message[]（只保留 user / assistant / toolResult 三种角色）。
  3. 组装 llmContext = { systemPrompt, messages, tools }——tools 就是可调用的函数清单，会原样发给模型。
  4. resolveApiKey（支持会过期的 token）后调用 streamFunction(config.model, llmContext, { apiKey, signal })（306-310 行）。这里就是模型调用本身。

streamFunction 的默认实现是 pi-ai 的 streamSimple——coding-agent 在 sdk.ts 第 37 行用 setDefaultStreamFn(streamSimple) 安装它；provider-composer 再按 model.api 把请求路由到具体供应商的适配器（如 api/openai-responses.ts），发出真正的 HTTP 请求。

模型以流式事件返回，主循环 for await 逐条处理（315-359 行）：

  • start ——创建一条 partial 的 assistant 消息，立刻写回上下文并广播 message_start（TUI 马上开始画）
  • text_delta / thinking_delta / toolcall_delta ——增量更新 partial 消息，广播 message_update（打字机效果）
  • done —— response.result() 拿到最终完整 assistant 消息

5. 第 4 段：工具调用让循环再转一圈

最终消息里可能有 toolCall 内容（模型说"我想调用 grep"）。主循环抽出这些调用（222 行），走 executeToolCalls()（409 行）：

  1. 校验参数 validateToolArguments，跑 beforeToolCall 钩子（可以拦截/拒绝）
  2. 执行 tool.execute(...)（真实行为：读文件、跑 bash…也可能只有 JS 副作用）
  3. 跑 afterToolCall 钩子（可改写结果）
  4. 把结果包成 toolResult 消息，追加进上下文；hasMoreToolCalls = true

hasMoreToolCalls 让内层循环再走一次 streamAssistantResponse——模型现在能看到工具结果，于是可以继续说话或再调工具。这就是"一个 agent 能读文件、再决定改文件"的机制。

注意过滤条件 message.stopReason === "length"（230-233 行）：输出被 token 上限截断时，工具调用可能参数残缺，pi 会直接把它们全部标记失败而不是执行——防止执行半截参数。

6. 第 5 段：收尾与输出

当某轮不带 toolCall，turn_end 发出，shouldStopAfterTurn 钩子决定是否收手（252 行）；外层循环再检查有没有排队的 follow-up / steering 消息（261 行），没有就以 agent_end 结束，携带这一整轮追加进来的全部消息。AgentSession 收到后把最终 assistant 消息渲染到 TUI（message_update 让它一早就开始流式显示，所以观众感觉是"边说边出"）。稳定的会话还会被写进 session 文件，供下次恢复。
