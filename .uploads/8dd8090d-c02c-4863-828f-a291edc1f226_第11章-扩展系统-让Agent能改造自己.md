# 第11章：扩展系统 —— 让 Agent 能改造自己

前 10 章，Pi 的核心机制我们基本都拆完了：Agent Loop、模型调用、工具、消息、事件、上下文、压缩、会话。

拆的过程中你大概注意到一个反差——**这些核心都很"小"**。TUI 一万七千行是例外（那是另一个正交的 UI 库），真正管 Agent 行为的那部分，加起来不到两千行。可 Pi 实际能做的事情，远远超过这两千行的覆盖范围：

- 团队里要禁掉 `rm -rf`；
- 想接一个自建的 DeepSeek 网关当默认模型；
- 想要一个只有你们业务才有的 SQL 工具；
- 想让每条消息发出去之前自动带上当前时间。

这些需求，Pi 的源码里**一行都没有**。它们从哪儿来？

答案是**扩展系统**。这也是 Pi 五根定制杠杆里最粗的一根（第 1 章 §3.2 讲过：扩展、技能、提示词模板、主题、Pi Package）。前 10 章反复出现的那句"扩展可以拦截工具调用""扩展可以改写消息""扩展可以预处理上下文"，指的都是它——但我们一直没打开这个盒子。

这一章就来打开。

> **本章最重要的一句话：扩展系统不是"往内核里注入魔法"，而是 Pi 在 Agent 工作流的关键点广播事件——0.99 的 `ExtensionEvent` 有 32 个顶层成员，`pi.on` 暴露 41 个重载——再由扩展决定要不要介入。这是一种"用约定（事件名 + 返回值协议）换灵活（不改源码）"的设计。而在 0.99，它更进一步：扩展不只能在场边拦事件，还能往场上注册 provider、虚拟模型、MCP 服务器。**

> 本章起延续第 7 章的进阶视角。第 7 章讲的是"事件系统"这个神经系统；本章讲的是"谁来接这根神经、以及除了接线还能干别的什么"。

## 一、问题：Pi 不可能预知你的需求

### 1.1 一个真实需求：禁掉 rm -rf

假设你在一个团队里推行 Pi。第一天就有人提："Agent 趁我不注意跑了个 `rm -rf`，把构建产物目录连着一个手写的脚本一起删了。给我加个拦截。"

最直接的想法是：**改 Pi 源码**，在工具执行前加一段判断。你 fork 了仓库，在 `bash` 工具里加了三行，跑通了。三个月后 Pi 发了新版本，你想合并上游——你加的那三行和上游重构过的工具代码撞在一起，手动解决冲突；下周又更新，又冲突。**你维护的不再是"一个团队策略"，而是"Pi 的一个私有分支"。**

这就是"给内核打补丁"的老路：功能是加上了，代价是永久性的合并税。

**更好的想法是：别动内核，让 Pi 主动把"我要执行工具了，要不要拦"这个决策点交出来。** 你在外面写一段自己的代码，回答"要拦"就行。内核一行不改，Pi 升级你只需要 `npm update`。

这段"外面的代码"就是**扩展**。

### 1.2 扩展是什么：一个 .ts 文件 + 一个工厂函数

先看最小的扩展长什么样（仓库 `examples/extensions/hello.ts`，删减）：

```typescript
import { Type } from "@earendil-works/pi-ai";
import { defineTool, type ExtensionAPI } from "@earendil-works/pi-coding-agent";

export default function (pi: ExtensionAPI) {
    pi.registerTool({
        name: "hello",
        label: "Hello",
        description: "A simple greeting tool",
        parameters: Type.Object({ name: Type.String() }),
        async execute(_id, params) {
            return { content: [{ type: "text", text: `Hello, ${params.name}!` }], details: {} };
        },
    });
}
```

就这些。**扩展是一个导出了默认函数的 TypeScript 模块**，那个函数叫**工厂函数**（factory）。Pi 启动时会找到它、调用它，把 `pi` 对象（类型是 `ExtensionAPI`）交到你手里。你在这个函数里做的一切——注册工具、注册命令、订阅事件——都写进 Pi 内部的一张张表里。

工厂函数签名在 `extensions/types.ts`：`ExtensionFactory = (pi: ExtensionAPI) => void | Promise<void>`。**支持 async**，所以你在加载时也能 `await` 一些准备工作。

> 一个日常类比：扩展就像一个**新员工**，工厂函数是它的**入职流程**，`pi` 对象是它**领到的工牌**。入职时能登记自己要负责哪些岗位（注册工具/命令），也能在公告栏上贴"这类事我要过问"（订阅事件）。至于工牌上有些门禁现在刷不开——那是下一节要讲的"时机矛盾"，先记住这个概念。

### 1.3 扩展能干什么：五类注册 + 一类订阅

`pi` 对象上的方法，按用途可以分六类（`ExtensionAPI`，`extensions/types.ts`）：

| 类别 | 方法（举例） | 效果 |
|------|------------|------|
| **订阅事件** | `on()` | 在关键点介入，能拦截、能改写（本章主角） |
| **注册工具** | `registerTool()` | 给模型加新工具（第 5 章讲的 `ToolDefinition`） |
| **注册命令/快捷键/flag** | `registerCommand()` / `registerShortcut()` / `registerFlag()` | 加 `/xxx` 命令、键位、CLI 参数 |
| **注册渲染** | `registerMessageRenderer()` / `registerEntryRenderer()` / `registerMarkdownTransformer()` | 定制消息/条目在终端里怎么画 |
| **动作** | `sendMessage()` / `sendUserMessage()` / `appendEntry()` / `exec()` / `setActiveTools()` / `setModel()` | 干活 |
| **0.99 起·注册生态资源** | `registerProvider()` / `registerVirtualModel()` / `registerMcpServer()` | 往场上加"人"（详见 §五） |

最后一类是 0.99 的分水岭——**扩展从"只能在场边拦一下"升级成"能注册生态资源"**。这是本章与旧版最大的差异，单独用 §五 讲。

先看整体形状。

![扩展的解剖](assets/260930-ch11-extension-anatomy.svg)

**配图说明**：一张图看清"扩展在 Pi 里是什么"。左侧是扩展文件——一个导出工厂函数的 `.ts`；中间是工厂函数收到的 `pi`（`ExtensionAPI`）；工厂函数里的每次 `pi.on(...)` / `pi.registerTool(...)` 都会往 `Extension` 对象的若干张表（`handlers` / `tools` / `commands` / `flags` / `shortcuts`）里写一项。右侧是 `ExtensionRunner`——它持有所有 `Extension` 对象，负责在运行时把事件派发给这些表。图底部标出关键分界：表是"注册期"填的，`ExtensionRunner` 是"运行期"用的——这条缝就是下一节要讲的"两阶段绑定"。

## 二、第一个回答：Pi 不知道你的需求，凭什么能扩展？

### 2.1 答案是"关键点广播"

Pi 不需要预知"你要禁 rm -rf"。它只做一件事：把 Agent 工作流里**所有值得介入的关键点**，在发生时广播出去。

```
Pi 内部（不知道你是谁）：
    "我要执行工具了，toolName = bash" ──emit──▶ 📡
    "我要发请求给 LLM 了，这是 messages" ──emit──▶ 📡
    "这一轮结束了" ──emit──▶ 📡
                                  │
                          ┌───────┴────────┐
                          ▼                ▼
                    你的扩展          别人的扩展
                 （订阅 tool_call）  （订阅 message_end）
```

这就是第 7 章讲的**管道 B**：Agent 会**停下来等**扩展的 handler 返回，因为它要读返回值才能决定下一步。扩展回答"拦"，它就拦；扩展返回一份新的 `messages`，它就改用新消息发请求。

**一句话把矛盾解开**：Pi 不负责"实现你的需求"，它负责"把决定权交出去"。32 个广播频道（下面就要数），你挑关心的订阅。

### 2.2 数一数：32 个顶层成员

事件类型叫 `ExtensionEvent`，定义在 `extensions/types.ts`。它是一个大联合类型。数清楚它到底有多少成员，是理解"覆盖面有多全"的第一步。

**统计口径先说清**：`ExtensionEvent` 里直接列出的**联合成员**有 32 个。其中有 3 个成员本身是"子联合"——`SessionEvent`、`ToolCallEvent`、`ToolResultEvent`——**每个只算 1 个顶层成员**（它们内部各含多个具体事件，在后面括注里展开）。这就是"32 个顶层成员"的口径。

| 分组 | 顶层成员 | 具体事件（子联合展开） |
|------|---------|----------------------|
| **启动/资源** | `project_trust`、`resources_discover`、`mcp_servers_change` | —— |
| **会话** | `SessionEvent` ×1 | `session_start` / `session_info_changed` / `session_before_switch` / `session_before_fork` / `session_before_compact` / `session_compact` / `session_compact_failed` / `session_shutdown` / `session_before_tree` / `session_tree`（10 个） |
| **上下文/请求** | `context`、`context_with_system`、`cache_warming_decision`、`before_provider_request`、`before_provider_headers`、`after_provider_response`、`provider_stream_event`、`before_agent_start` | —— |
| **Agent 生命周期** | `agent_start`、`agent_end`、`agent_before_settle`、`agent_settled` | —— |
| **UI 提示** | `ui_prompt_start`、`ui_prompt_end` | —— |
| **Turn / Message** | `turn_start`、`turn_end`、`message_start`、`message_update`、`message_end` | —— |
| **工具执行** | `tool_execution_start`、`tool_execution_update`、`tool_execution_end` | —— |
| **模型** | `model_select`、`thinking_level_select` | —— |
| **用户命令 / 输入** | `user_bash`、`input` | —— |
| **工具决策** | `ToolCallEvent` ×1、`ToolResultEvent` ×1 | 按工具名分 9 个变体：`bash` / `powershell` / `read` / `edit` / `write` / `grep` / `find` / `ls` + `CustomToolCallEvent`（自定义工具） |

数一下：3 + 1 + 8 + 4 + 2 + 5 + 3 + 2 + 2 + 2 = **32**。

> 对照第 7 章 §3.3 讲的"管道 A 收不到"清单：`input` / `before_agent_start` / `context` / `context_with_system` / `tool_call` / `tool_result` / `message_end` / `cache_warming_decision` / `turn_end` / `agent_before_settle` / `user_bash`——它们全部在这 32 个里面。**扩展系统（管道 B）见得到的工作流关键点，是内核 10 种 `AgentEvent`（管道 A 的事件源）的好几倍。**

### 2.3 `pi.on`：41 个重载 + 返回注销函数

事件注册的唯一入口是 `pi.on(event, handler)`。它有三个要点：

**要点一：类型层面有 41 个重载。** `ExtensionAPI.on` 在 `extensions/types.ts` 里对每种事件名写了一个专门的重载，让 `event` 和 `handler` 的参数类型精确对应。为什么 41 而不是 32？因为 `SessionEvent` 在联合里算 1 个成员，但 `on()` 给那 10 个 `session_*` 事件**各自**写了一个重载。算术是：`32 - 1 + 10 = 41`。

**要点二：返回一个注销函数。** 你调 `pi.on(...)`，拿到的是一个 `() => void`，调用它就取消这次订阅。实现极简（`loader.ts` 的 `createExtensionAPI`）：

```typescript
on(event: string, handler: HandlerFn): () => void {
    assertActive();
    const registeredHandler: HandlerFn = (...args) => handler(...args);
    const list = extension.handlers.get(event) ?? [];
    list.push(registeredHandler);          // 往 Map<事件名, handler[]> 里追加
    extension.handlers.set(event, list);

    return () => {                         // ← 注销函数
        const handlers = extension.handlers.get(event);
        if (!handlers) return;
        const handlerIndex = handlers.indexOf(registeredHandler);
        if (handlerIndex === -1) return;
        handlers.splice(handlerIndex, 1);
        if (handlers.length === 0) extension.handlers.delete(event);
    };
}
```

每个 `Extension` 对象内部有一张 `handlers: Map<string, handler[]>`。注册就是往对应 key 下追加一项；注销就是把那一项 splice 掉。

**要点三：派发用的是快照。** `ExtensionRunner` 每次派发前都调 `snapshotEventHandlers()`（`runner.ts`）：

```typescript
function snapshotEventHandlers(extensions: Extension[], event: ExtensionEvent["type"]) {
    return extensions.map((ext) => ({ ext, handlers: ext.handlers.get(event)?.slice() ?? [] }));
}
```

注意那个 `.slice()`——**先复制一份再遍历**。所以 handler 在派发**过程中**调 `pi.on` 新增、或调注销函数移除，**只对后续派发生效**，不影响正在跑的这一轮。这是个很实际的保护：你在 handler 里动态换策略，不会把当前这轮遍历搞乱。

> **一个值得记住的坑（0.99 起）**：会话替换（`newSession` / `fork` / `switchSession`）或 `reload` 之后，你先前捕获的 `pi`/`ctx` 会**变陈旧**——再调用会抛错（`invalidate` / `assertActive`，见 `loader.ts` 的 `createExtensionRuntime` 与 `runner.ts` 的 `ExtensionRunner.createContext`）。提示语写得很直白：替换后的工作请放进 `withSession` 回调，用回调收到的那个新 `ctx`；`await ctx.reload()` 之后不要再用旧 `ctx`。

### 2.4 四种事件模式：扩展能用什么方式介入

不是所有事件都能改写。派发方法的行为决定了"这个事件上你能干什么"，一共四种模式：

| 模式 | 你怎么介入 | 典型事件 | 返回值的处理 |
|------|-----------|---------|------------|
| **通知型** | 只能看 | `turn_start` / `message_update` / `agent_end` / `model_select` | 返回值被忽略（但仍 `await`，作同步屏障） |
| **取消型** | 一票否决 | `session_before_switch` / `session_before_fork` / `session_before_compact` / `session_before_tree`、`project_trust` | 返回 `{ cancel: true }`，派发立即短路 |
| **修改型** | 链式改写 | `context` / `context_with_system` / `tool_result` / `message_end` / `input` / `before_agent_start` / `before_provider_request` | 每个 handler 收到上一个的输出，继续改 |
| **短路型** | 抢先接管 | `tool_call`（`block`）、`input`（`handled`）、`user_bash`（`result`） | 返回特定结果立即结束派发 |

这张表在源码里的落点，是 `runner.ts` 里的几个派发方法：

- **`emit()`** —— 通用派发，处理通知型 + 取消型。串行 `await`、每个 handler 包 `try-catch`、忽略返回值（`session_before_*` 例外，读 `cancel`）。**注意它的类型参数是 `RunnerEmitEvent`，而不是 `ExtensionEvent`**——见 §2.7。
- **`emitToolCall()`** —— `tool_call` 专用，读返回值、`block` 短路、**不包 `try-catch`**（下一节讲为什么）。
- **`emitToolResult()` / `emitContext()` / `emitMessageEnd()` / `emitInput()` / `emitBeforeAgentStart()` / `emitBeforeProviderRequest()`** …… 各自的改写型事件一个方法，模式是"链式传递"：把上一个 handler 的结果作为变量传给下一个。
- **`emitBoundary()`** —— `turn_end` / `agent_before_settle` 专用（§2.7）。

### 2.5 六个最有代表性的介入点，各配一个"能干什么"

**① `tool_call`（执行前，能拦）** —— 就是开篇那个需求：

```typescript
pi.on("tool_call", async (event) => {
    if (event.toolName === "bash" && /rm\s+-rf/.test(event.input.command)) {
        return { block: true, reason: "禁止递归删除：请改用 trash 或明确路径删除" };
    }
    return undefined;   // 放行
});
```

`block` 立即短路，后续 handler 不再跑。被拦的调用会变成一条 `isError: true` 的 ToolResultMessage 回给模型（第 5 章 §三 第 3 步 `beforeToolCall` 的底层就是这条管道）。`event.input` **可变**——你也可以原地改参数（"把 `rm -rf` 替换成 `trash`"），看 `ToolCallEvent` 的类型注释。

**② `context`（发 LLM 前，能改 messages）** —— 注入当前时间：

```typescript
pi.on("context", async (event) => ({
    messages: [...event.messages, { role: "user", content: `当前时间是 ${new Date().toISOString()}` }],
}));
```

注意 handler 只看到**不含 system 的对话**——prompt 和工具声明由 Pi 保管，handler 返回后 Pi 会把它们还原回去（`runner.ts` 的 `restoreSystemMessages`）。这样设计的目的是保护缓存前缀。真想连 system 一起接管，用 0.99 新增的 `context_with_system`（第 7 章 §4.6 讲过）。

**③ `input`（用户提交后，能改写或接管）** —— 过滤输入：

```typescript
pi.on("input", async (event) => {
    if (event.text.startsWith("/secret")) {
        return { action: "handled" };              // 我自己处理，不给 Agent
    }
    if (event.text.includes("TODO")) {
        return { action: "transform", text: event.text.replace("TODO", "") };
    }
    return { action: "continue" };
});
```

`handled` 短路、`transform` 链式改写（`InputEventResult`）。

**④ `message_end`（消息定稿，能替换）** —— 脱敏：

```typescript
pi.on("message_end", async (event) => {
    if (event.message.role !== "assistant") return;
    const redacted = redactSecrets(event.message);   // 返回新的 assistant 消息
    return redacted ? { message: redacted } : undefined;
});
```

替换必须**保持原 role**，否则 `emitMessageEnd` 报错并跳过（`runner.ts`）。

**⑤ `session_before_switch`（会话切换前，能一票否决）** —— 这是第 10 章说的"扩展可以拦截会话操作"的真身。仓库 `examples/extensions/confirm-destructive.ts` 就是这个：

```typescript
pi.on("session_before_switch", async (event, ctx) => {
    if (!ctx.hasUI) return;
    if (event.reason === "new") {
        const ok = await ctx.ui.confirm("Clear session?", "This will delete all messages.");
        if (!ok) {
            ctx.ui.notify("Clear cancelled", "info");
            return { cancel: true };                 // 一票否决
        }
    }
});
```

**⑥ `turn_end` / `agent_before_settle`（边界，能写历史 + 续跑）** —— 这个特殊，见 §2.7。

### 2.6 完整闭环：rm -rf 是怎么被拦住的

把 ① 的链路从头追到尾，你就理解"扩展介入"这个词的全部含义：

```
用户/模型触发一次 bash 调用 { command: "rm -rf build src/gen.ts" }
    │
    ▼  Agent Loop 准备执行工具，走第 5 章的五步管道第 3 步
    ▼  AgentSession._beforeToolCall  →  ExtensionRunner.emitToolCall(event)
    │
    ▼  逐个 handler（快照）：你的 handler 命中，返回 { block: true, reason }
    │
    ▼  block 立即短路，emitToolCall 返回该结果
    │
    ▼  AgentSession 把 block 翻译成一条错误 ToolResultMessage：
       { role: "toolResult", isError: true, content: "禁止递归删除：..." }
    │
    ▼  工具**没有被执行**；这条错误消息进入对话历史
    │
    ▼  下一轮发给 LLM，模型看到"被拒绝了"，自己换个做法或向用户解释
```

注意最后一环——**模型会"知道"命令被拦了**。这是第 5 章那条哲学的延续：错误是给模型的反馈，不是给框架的终止信号。工具被拦不会打断循环，而是变成下一步决策的输入。

### 2.7 0.99 破坏性变更：边界事件不再走 `emit()`

`turn_end` 和 `agent_before_settle` 这两个事件，0.99 起被单独拎出来，变成了**可动作化的边界事件**。这带来一处**破坏性变更**，必须单独说清（第 7 章 §4.7 已从事件系统口径讲过，这里从扩展系统口径对齐）。

**变更本身**：`ExtensionRunner.emit()` **不再接受** `turn_end` / `agent_before_settle`。看 `runner.ts` 的类型定义：

```typescript
type RunnerEmitEvent = Exclude<
    ExtensionEvent,
    | ToolCallEvent | ToolResultEvent | ProjectTrustEvent | UserBashEvent
    | ContextEvent | ContextWithSystemEvent | CacheWarmingDecisionEvent
    | BeforeProviderRequestEvent | BeforeProviderHeadersEvent | BeforeAgentStartEvent
    | MessageEndEvent | ResourcesDiscoverEvent | InputEvent
    | TurnEndEvent | AgentBeforeSettleEvent
>;
```

`emit()` 的入参是 `RunnerEmitEvent`，这个 `Exclude` 列表**把 15 种事件挡在外面**（`turn_end` / `agent_before_settle` 是其中两个）。它们各有专属方法——这也解释了一个现象：`pi.on("turn_end", ...)` 能注册，但派发它的**不是** `emit()`。

**新方法 `emitBoundary()`**：Host（`AgentSession`）改用 `ExtensionRunner.emitBoundary(baseEvent, buildContext)` 派发。第二个参数 `buildContext` 负责把当前已追加的 entries 投影成一份 `BoundaryContextPreview`，每个 handler 跑完都重建一次：

```typescript
const handlerResult = (await handler(event, ctx)) as BoundaryResult | undefined;
if (handlerResult?.entries !== undefined) entries = handlerResult.entries;
if (handlerResult?.continue !== undefined) shouldContinue = handlerResult.continue;
```

**handler 能返回什么**：`BoundaryResult = { entries?, continue? }`。

- `entries` 是一批**结构性 entry 草稿**（`SessionBoundaryDraft`）：`custom` / `custom_message` / `context_edit` / `compaction` 四种——handler 可以往会话树里**持久化**它们。
- `continue` 表示"**确保再发起一次 provider 请求**"（工具结果、steering、followUp 的调度能满足它，不额外多请求一次）。

于是扩展能做到一件以前做不到的事：**在"历史已经定稿、但这一轮还没彻底翻篇"的位置，一边写历史一边续跑**。第 1 章 §3.2 提到的"loop 模式（拦截 `turn_end` 再触发下一轮）"，0.99 起就在这个位置实现。

**配套的内核侧变更 `finishTurn`**：内核（`@earendil-works/pi-agent-core`）的 `AgentLoopConfig` 用 `finishTurn` 取代了旧的 `shouldStopAfterTurn`（这与第 3 章口径一致）。它在 **assistant 消息和它的全部工具结果定稿之后、内核 `turn_end` 事件之前**被调用，返回 `{ action: "end" | "continue" }`，**对正常 / 出错 / 中止三类响应都会运行**（出错/中止分支不读返回值，仍是硬退出）。`AgentSession` 把 `turn_end` 边界的 dispatcher 挂在这个 `finishTurn` 上；若某个 `turn_end` handler 要求续跑，wrapper 返回 `{ action: "continue" }` 交给内核。

> 一句话对齐第 7 章：**内核的 `finishTurn` 是"要不要在这一轮收尾"的钩子；扩展的 `turn_end` / `agent_before_settle` 边界是"我可以在这里写历史并决定续不续"的入口。两者互补，但都不是普通的 `emit()` 事件。**

## 三、第二个回答：工厂函数那么早执行，运行时的操作怎么办？

### 3.1 时机矛盾

§1.2 说扩展"就是一个工厂函数，在工厂里 `pi.on(...)` 注册"。看起来很简单。但你会立刻撞上一个矛盾：

**工厂函数是在 Pi 的启动加载阶段执行的——那时候 Agent 还不存在。**

具体点说，加载扩展的时候：SessionManager 还没建、Agent Loop 还没跑、模型还没确认、UI 还没起来。那么问题来了——如果你在工厂函数里写：

```typescript
export default function (pi) {
    pi.sendMessage({ customType: "init", content: "扩展已加载", display: true });
    // ↑ 这条消息发给谁？此时还没有会话。
}
```

会发生什么？发不出去。这个动作**在这个阶段没有意义**。

但你在**事件 handler 里**写同样的 `pi.sendMessage(...)`，就完全合理——那时会话早就跑起来了。

**同一个 `pi.sendMessage`，在工厂函数里调没意义，在 handler 里调是真实操作。** 怎么让同一个 API 自动适配两个阶段？

### 3.2 注册阶段：throwing stubs（调用就抛）

Pi 的解法叫**两阶段绑定**（two-phase binding）。第一阶段在 `loader.ts` 的 `createExtensionRuntime()` 里完成：**先把所有"操作型"方法填成"一调用就抛错"的桩（stub）**。

```typescript
export function createExtensionRuntime(): ExtensionRuntime {
    const notInitialized = () => {
        throw new Error("Extension runtime not initialized. Action methods cannot be called during extension loading.");
    };

    const runtime: ExtensionRuntime = {
        sendMessage: notInitialized,
        sendUserMessage: notInitialized,
        appendEntry: notInitialized,
        setSessionName: notInitialized,
        getActiveTools: notInitialized,
        setActiveTools: notInitialized,
        getCommands: notInitialized,
        // ...等等
        setModel: () => Promise.reject(new Error("Extension runtime not initialized")),
        createContext: notInitialized,
        // registerTool() 合法：加载期注册工具是正常的，所以 refreshTools 是空函数而非抛错桩
        refreshTools: () => {},
        // 注册型能力不抛错，而是排队（见 §5）
        flagValues: new Map(),
        pendingProviderRegistrations: [],
        pendingVirtualModelRegistrations: [],
        mcpServers: new McpServerRegistry(),
        // ...
    };
    return runtime;
}
```

两个细节值得注意：

1. **不是所有方法都是桩。** `refreshTools` 是空函数——因为"加载期注册工具"是**合法**的（工厂函数里 `pi.registerTool()` 很常见），只是那时还不需要刷新。`getFlag` 也能用，读的是加载期的待定值。
2. **注册型能力（0.99 起）用的是"排队"而非"抛错"。** `registerProvider` 在加载期把参数 push 进 `pendingProviderRegistrations`，等绑定后统一处理（§5 展开）。**这就是"声明意图"和"执行操作"被分开的又一个例子**——注册 provider 只需要"记下来"，不需要当时就有 ModelRegistry。

### 3.3 绑定阶段：`bindCore()` 把桩换成真实实现

第二阶段在 `runner.ts` 的 `ExtensionRunner.bindCore()` 里。Agent、SessionManager、ModelRegistry 都就绪之后，Host 调它，把真实实现赋值进那个**共享的 runtime 对象**：

```typescript
bindCore(actions: ExtensionActions, contextActions: ExtensionContextActions, providerActions?): void {
    // 把真实实现拷进共享 runtime —— 所有扩展的 API 都引用这一个对象
    this.runtime.sendMessage = actions.sendMessage;
    this.runtime.sendUserMessage = actions.sendUserMessage;
    this.runtime.appendEntry = actions.appendEntry;
    this.runtime.getActiveTools = actions.getActiveTools;
    this.runtime.setActiveTools = actions.setActiveTools;
    // ...
    this.runtime.createContext = () => this.createContext();

    // 上下文动作（供 ctx.* 使用）
    this.getModel = contextActions.getModel;
    this.isIdleFn = contextActions.isIdle;
    this.shutdownHandler = contextActions.shutdown;
    this.compactFn = contextActions.compact;
    // ...
}
```

**关键点：`pi` 对象上的方法只是"转发器"**。看 `loader.ts` 里的 `pi.sendMessage`：

```typescript
sendMessage(message, options): void {
    assertActive();
    runtime.sendMessage(message, options);   // ← 转发到共享 runtime
},
```

它转发给 `runtime.sendMessage`。而 `runtime.sendMessage` 在 `bindCore` 前是抛错桩、之后是真实实现。**`pi` 对象自始至终是同一个；变的只是它指向的那个 runtime 目标。** 于是：

- 在工厂函数里调 → 撞上桩 → 抛错（合理：这时调用没意义）。
- 在 handler 里调 → runtime 已被 `bindCore` 换过 → 真实操作。

**扩展代码对这个差异完全无感知**——你不用写 `if (isReady)`，也不用管什么时候绑定的。同一个 API，自动适配两个阶段。

> 为什么必须这么设计？因为**扩展模块的加载顺序，不能依赖"核心已经就绪"**。扩展们是并行/按目录顺序加载的，谁先谁后不确定；而 ModelRegistry、SessionManager 要等启动流程走到某一步才建好。如果工厂函数里必须拿到真实实现，就得强制"先建核心再加载扩展"，加载器立刻和启动流程耦合死。throwing stubs + bindCore 把这个耦合切开了：**加载器只负责"把扩展代码跑起来、把意图登记下来"；核心只负责"晚点来兑现"。** 这是"解耦加载顺序"的代价，也是它换来的收益。

### 3.4 注册型能力的排队 → flush

注册型能力把上面的模式又用了一遍。加载期调 `pi.registerProvider(...)`，进的是 `pendingProviderRegistrations` 队列；`bindCore()` 最后有一段**统一 flush**（`runner.ts`）：

```typescript
// Flush provider registrations queued during extension loading
for (const { name, config, extensionPath } of this.runtime.pendingProviderRegistrations) {
    try {
        if (providerActions?.registerProvider) providerActions.registerProvider(name, config);
        else this.modelRegistry.registerProvider(name, config);
    } catch (err) {
        this.emitError({ extensionPath, event: "register_provider", error: ... });
    }
}
this.runtime.pendingProviderRegistrations = [];

// 同理 flush pendingNativeProviderRegistrations 与 pendingVirtualModelRegistrations

// 从这里开始，注册/注销立即生效，不再需要 /reload
this.runtime.registerProvider = (name, config) => { /* 直接调 ModelRegistry */ };
```

注意最后一段：**flush 完就把 `runtime.registerProvider` 也换成了真实实现**。所以：

- **加载期注册** → 排队，`bindCore()` 时统一生效；
- **绑定后注册**（比如在命令 handler 里） → **立即生效**，不用 `/reload`。

**排队机制再次印证两阶段绑定**：注册型方法和操作型方法受同一条约束——"注册阶段"和"运行阶段"是两回事。

### 3.5 注册期与运行期的另一处边界：`ctx` 是"每次现造"的

顺带把另一个容易误会的点说清：事件 handler 拿到的 `ctx`（`ExtensionContext`）**不是**一个固定的对象，而是 `ExtensionRunner.createContext()` **每次现造**的（`runner.ts`）。它里面全是 getter，读的时候才去向 runner 要最新值：

```typescript
createContext(): ExtensionContext {
    const runner = this;
    return {
        get ui() { runner.assertActive(); return runner.uiContext; },
        get mode() { runner.assertActive(); return runner.mode; },
        get model() { runner.assertActive(); return getModel(); },
        get scopedModels() { runner.assertActive(); return getScopedModels(); },
        // ...
        compact: (options) => { runner.assertActive(); runner.compactFn(options); },
    };
}
```

所以"运行时换模型/换 UI/换会话"之后，同一个 handler 下次拿到的 `ctx` 会反映新值。代价是这些 getter 都带 `assertActive()`——实例失效后读它就抛错（§2.3 那个坑）。

## 四、第三个回答：扩展是第三方代码，崩了、作恶了怎么办？

### 4.1 错误隔离：一个扩展崩了不能拖垮核心

扩展是别人写的代码。它可能在 handler 里抛异常、可能死循环、可能逻辑写错。**一个扩展崩了，绝不能把整个 Agent Loop 带崩。**

Pi 的做法是**在每个 handler 外面包 `try-catch`，把异常编码成一条 `ExtensionError` 往外报**，不打断派发。看 `emit()` 的核心：

```typescript
for (const { ext, handlers } of snapshotEventHandlers(this.extensions, event.type)) {
    for (const handler of handlers) {
        try {
            const handlerResult = await handler(event, ctx);
            // ...
        } catch (err) {
            this.emitError({ extensionPath: ext.path, event: event.type, error: message, stack });
            //  ↑ 只上报，不重抛：下一个扩展继续跑
        }
    }
}
```

### 4.2 唯一的例外：`emitToolCall` 是 fail-closed

**只有 `tool_call` 的派发完全不包 `try-catch`**（`runner.ts` 的 `emitToolCall`）：

```typescript
async emitToolCall(event: ToolCallEvent): Promise<ToolCallEventResult | undefined> {
    const ctx = this.createContext();
    let result: ToolCallEventResult | undefined;
    for (const { handlers } of snapshotEventHandlers(this.extensions, "tool_call")) {
        for (const handler of handlers) {
            const handlerResult = await handler(event, ctx);   // ← 没有 try-catch！
            if (handlerResult) {
                result = handlerResult as ToolCallEventResult;
                if (result.block) return result;
            }
        }
    }
    return result;
}
```

扩展在这里抛错，会一路冒泡到调用方 `AgentSession._beforeToolCall`，被包成 "Extension failed, blocking execution" 再抛——结果就是**这次工具调用被拦掉**。

> **为什么这里要 fail-closed（宁可错杀，不放过）？** 因为 `tool_call` 是**安全闸门**。想象你的扩展就是那个"禁 rm -rf"的守门员——它本意是拦危险命令，但代码里抛了个异常。这时候应该"放行"还是"拦下"？显然应该拦下：**一个本想拒绝的闸门，不能因为自己出错就变成放行。** 其余派发方法则是 fail-safe——某个扩展挂了，只丢它自己的改动，其他扩展和核心照常。两种策略的选择标准就一句：**这个位置出错的代价，是漏过一个危险操作，还是少一次无关紧要的通知。**

> 顺带一个对照：`emitUserBash()` 会捕获并上报错误，但**随后把错误重新抛出**（`throw err`）——它想"上报 + 不静默吞掉"，是第三种风格。理解这三种风格的差别，比记住"有没有 try-catch"更有用。

### 4.3 最小权限门面：三层 API

除了错误隔离，还有一层保护：**普通事件 handler 拿不到危险方法**。`pi` 上确实有 `fork` / `switchSession` / `reload` 这类能"劫持会话"的方法，但它们**不在 `ExtensionContext` 上**。Pi 把交给扩展的对象分成了三层（`extensions/types.ts`）：

| 门面 | 谁拿到 | 能力 |
|------|-------|------|
| **`ExtensionAPI`**（`pi`） | 工厂函数 | **注册能力**：`on` / `registerTool` / `registerProvider` … |
| **`ExtensionContext`**（`ctx`） | 事件 handler、工具 execute | **只读查询 + 受控动作**：`ui` / `model` / `sessionManager`(只读) / `abort()` / `compact()` … |
| **`ExtensionCommandContext`** | 命令 handler（用户主动触发） | **特权操作**：`newSession` / `fork` / `navigateTree` / `switchSession` / `reload` |
| **`ExtensionToolContext`** | 工具 `execute()` | `ExtensionContext` + `tools` + `executeTool()` |

**为什么命令上下文才给特权方法？** 因为命令是**用户主动敲的**（`/deploy`），一个"用户自己触发的动作"里切换会话是合理的。而事件 handler 是**在 Agent 跑的时候被动触发的**——一个工具回调里突然 `switchSession`，会话状态会乱。所以 Pi 用**门面分层**把"哪些能力在什么场合可用"编码进了类型：想让扩展切会话，就得把它做成命令。

### 4.4 `ExtensionContext` 现在有什么：0.99 的能力清单

`ExtensionContext` 是三层里最常用的一个。0.99 起它长这样（`extensions/types.ts`）：

| 成员 | 能干什么 | 备注 |
|------|---------|------|
| `ui: ExtensionUIContext` | `select` / `confirm` / `input` / `notify` / 设置组件… | 交互 UI 全套 |
| `mode` | `"tui" \| "rpc" \| "json" \| "print"` | 判断运行模式 |
| **`hasUI: boolean`** | 当前是否有可弹窗的 UI | **0.99 新增**，TUI / RPC 为 `true` |
| `cwd: string` | 工作目录 | |
| `sessionManager: ReadonlySessionManager` | **只读**地读会话历史 | 见下 |
| `modelRegistry` / `model` | 模型注册表 / 当前模型 | |
| **`scopedModels: readonly ScopedModel[]`** | 本会话作用域内的模型快照 | **0.99 新增**，空 = 未配置 scoping |
| `thinkingLevel?` | 当前思考级别 | |
| `isIdle()` | Agent 是否空闲 | |
| **`isProjectTrusted(): boolean`** | 项目本地信任是否生效 | **0.99 新增** |
| `signal` / `abort()` | 中断信号 / 主动中断 | |
| `hasPendingMessages()` | 是否有排队消息 | |
| **`shutdown(): void`** | 优雅退出 pi | **0.99 新增：所有上下文都可用** |
| **`getContextUsage(): ContextUsage \| undefined`** | 上下文用量（token / 窗口 / 百分比） | **0.99 新增** |
| **`compact(options?)`** | 触发一次压缩（不等待完成） | **0.99 新增** |
| **`getSystemPrompt(): string`** | 读当前生效的系统提示 | **0.99 新增** |

新增的这几项，归位也很清楚：`hasUI` / `scopedModels` / `model` / `sessionManager` / `getContextUsage` / `getSystemPrompt` 是**只读查询**；`abort` / `compact` / `shutdown` 是**受控动作**（触发一个明确的行为，但不改会话结构）。它们都没有打破"普通 handler 拿不到危险方法"这条线——`fork` / `switchSession` 依旧只在命令上下文里。

### 4.5 一个必须解释的设计：`sessionManager` 为什么是只读

`ExtensionContext.sessionManager` 的类型是 `ReadonlySessionManager`——**能读历史，不能直接写**。

为什么？回到第 10 章 §六 那句结论：**`SessionManager` 是 provider context 的权威来源**，直接改历史要走它、还要 `refreshContext()` 同步。如果给事件 handler 一个可写的 `sessionManager`，一个不小心就会在 Agent 跑的过程中把会话树改乱（第 10 章还专门讲了"直接赋值 `agent.state.messages` 已经不管用"这个坑）。

所以事件 handler 要写会话，得走 `pi` 上的**受控动作**：`pi.sendMessage()`（发自定义消息）、`pi.appendEntry()`（追加自定义 entry，不进 LLM 上下文）、`pi.setLabel()`。要写结构化 entry / 改上下文投影，则走 §2.7 讲的**边界事件**（`turn_end` 的 `entries` 草稿）。**"读给只读对象、写给受控动作"**——这就是最小权限在同一件事上的体现。

## 五、0.99 的重点：扩展从"拦事件"升级为"注册生态资源"

前面四节讲的扩展，本质都是"**在场边喊话**"——Pi 广播事件，扩展决定要不要拦、要不要改。0.99 给 `ExtensionAPI` 加了一组新方法，让扩展可以"**往场上加人**"：注册 provider、虚拟模型、MCP 服务器。

| 方法 | 注册什么 | 解决什么问题 |
|------|---------|------------|
| `registerProvider(name, config)` / `registerProvider(provider)` | 一个模型 provider | 接入新模型服务、覆盖已有 provider 的 `baseUrl`、提供 `oauth`（供 `/login`）、提供自定义 `streamSimple` |
| `registerVirtualModel(model)` | 一个**虚拟模型** | 一个"可被选中、但每次请求路由到不同物理模型"的目录项 |
| `registerMcpServer(name, config)` | 一个 MCP 服务器 | 把"接入一个新工具源"也变成扩展的事 |

![能力表面：拦截 vs 注册](assets/260930-ch11-capability-surface.svg)

**配图说明**：把扩展的两张"能力表面"并排放。**左侧是拦截面**——事件总线：Pi 广播 32 类关键点，扩展 `pi.on` 订阅、用返回值干预（拦、改、否决）。它是"场边喊话"，作用在**已经发生的事**上。**右侧是注册面**（0.99 新增）——`registerProvider` / `registerVirtualModel` / `registerMcpServer`：扩展把**新资源**登记进 ModelRegistry / MCP 注册表，作用在"**接下来会发生的事**"上。图中间标出两条共同的时间线：**加载期 → 排队 → `bindCore` flush → 运行期立即生效**——注册面并没有另起炉灶，它复用了第 §三 那套两阶段绑定。

### 5.1 三种注册能力的时序要点

**加载期排队 / 绑定后即时。** 三者都是：加载期调用进队列（`pendingProviderRegistrations` / `pendingVirtualModelRegistrations` / MCP 注册表），`bindCore()` 统一 flush；绑定之后调用**立即生效**，无需 `/reload`。这直接复用 §3.4 讲的两阶段绑定。

**各自的生命周期细节**：

- **Provider**：`registerProvider(name, { baseUrl, api, models, oauth, streamSimple, ... })`。规则是"若给了 `models` 就替换该 provider 全部模型；只给 `baseUrl` 就改写已有模型的地址"。对应 `unregisterProvider()`（会恢复被覆盖的内置模型）。
- **MCP 服务器**：加载期注册的在 `session_start` 连接，之后注册的立即连接。**注册不落盘**——每次加载都要重新注册；`mcp.json` 里的同名条目优先；名字被别的扩展占用会抛错。对应 `unregisterMcpServer()` / `getMcpServers()`。
- **虚拟模型**：见下，单独展开。

### 5.2 展开：虚拟模型到底解决什么问题

"注册一个虚拟模型"听起来抽象，但它解决的是一个很具体的痛点。

**场景**：你想让"简单任务走便宜模型、困难任务走贵模型"，但又不想每次都手动切。你希望 Agent 里永远只有一个可选项叫"smart-router"，选它之后由你的逻辑按请求来分配。

**虚拟模型就是这个可选项**。`registerVirtualModel()` 注册一个"目录项"：它**能被 `/model` 选中**，但**永远不会真的发给任何 provider**——因为它的 `route(request, ctx)` 会在每次请求时决定用哪个**物理**模型。

```typescript
pi.registerVirtualModel({
    provider: "corp",          // 挂在哪个 provider id 下（可以是已有 provider）
    id: "smart-router",
    name: "Smart Router",
    route: async (request, ctx) => {
        // request.reason: "user" | "continuation" | "retry" | "direct"
        // request.messages: 本次要发的对话
        if (request.reason === "user" && isHard(request.messages)) {
            return { model: getModel("anthropic", "claude-sonnet-4-5"), thinkingLevel: "high" };
        }
        return { model: getModel("deepseek", "deepseek-v4-flash"), thinkingLevel: "off" };
    },
});
```

几个要点（`virtual-models.ts`）：

- **选择的记录用虚拟模型名**：你选了 `smart-router`，`ctx.model`、`model_change` 条目记的都是它。
- **assistant 消息记物理模型**：真正发出去、真正回话的是 `claude-sonnet-4-5` 或 `deepseek-v4-flash`，assistant 消息里记的是那个物理模型。**虚拟模型从不抵达 provider**（`VIRTUAL_MODEL_API = "pi-virtual"`，未路由的请求会失败）。
- **路由发生在绑定之后**，所以 `ctx` 是**按请求现造**的（`loader.ts` 的 `registerVirtualModel` 里：`route: (request) => model.route(request, runtime.createContext())`）。这也解释了它为什么天然要排队——路由要等到运行时才跑。
- **`reason` 告诉你"为什么路由"**：`user`（用户发消息后的首个请求）、`continuation`（工具结果之后的续跑）、`retry`（失败重试）、`direct`（Agent Loop 之外，如压缩摘要）。你据此区分"该用哪个模型"。
- **路由可带状态**（`route` 返回 `state`），状态存在会话分支上的 `pi.virtual-model-state` 自定义条目里——所以回退分支时路由状态也跟着回退。

> 一句话：**虚拟模型是在"模型选择"这一层加的一层可编程间接。** 它是 0.99 注册型能力的典型代表——扩展不再只是"看到请求改一改"（那是 `before_provider_request`），而是"**重新定义一个可选项**"。

### 5.3 `mcp_servers_change`：新增事件与"谁负责连接"

注册型能力还带出一条新事件 `mcp_servers_change`（`McpServersChangeEvent`，携带变更后的全部服务器）。它的语义有个不寻常之处：

> **处理这个事件，就等于宣告"本扩展负责连接这些服务器"。** 否则 `ExtensionRunner` 会把"无人处理的注册"上报成扩展错误（`reportUnhandledMcpServers()`，`runner.ts`；监听器在 `bindCore()` 里装到 `runtime.mcpServers` 上）。

这就是内置 MCP 扩展的工作方式：它订阅 `mcp_servers_change`，读到别人 `registerMcpServer` 的服务器，去连接、把工具注册成 `mcp__<server>__<tool>`（`extensions/mcp/index.ts`）。**如果另一个第三方 MCP 扩展替换了内置的那个（`replaceable`，见 §七），内置的不再处理该事件，注册的服务器就会以"没人连"上报——设计上是有意暴露这种"注册了却没人管"的状态。**

### 5.4 工具暴露模型：注册 ≠ 模型看得见（呼应第 5 章）

注册型能力让 Pi 里的资源变多了。资源一多，就有个老问题——**多了不能全塞给模型**。第 5 章 §二 已经讲过 `ToolExposure`，本章从"扩展能注册什么"的角度呼应一遍，保证口径一致。

`registerTool()` 注册的工具带 `exposure` 字段，决定"**模型怎么接触到这个工具**"（`extensions/types.ts`）：

| 取值 | 含义 |
|------|------|
| `direct` | 激活时向模型声明，且可被调用（默认） |
| `model-only` | 激活时向模型声明，但**永不可被其他工具调用**（编排/交互类，如 `codemode`、`tool_search`） |
| `codemode` | **只要注册就可从 codemode 脚本调用**；不显式激活则不向模型声明，codemode 描述里会列出它 |
| `deferred` | 同 `codemode`，但 codemode 描述里**不**列出它；`tool_search` 能搜到 |
| `hidden` | 已注册但谁都够不着，激活也无效 |

配套的 `ToolLoadout` / `prepareLoadout()`（`ToolDefinition.prepareLoadout`）：工具活跃集变化时回调，喂给它一个 `ToolLoadout`——含 `declared`（声明给模型的）/ `callable`（`ctx.executeTool()` 能调到的）/ `registered`（全部注册的）三份名单，外加 `getExposure(name)` / `getNamespace(name)`。返回 `ToolLoadoutChanges` 可以改写声明描述（`descriptions`）或临时隐藏声明（`hiddenDeclarations`）。

**与 codemode 的联动**是这套模型最实用的部分（`extensions/codemode/tool.ts`）：codemode 脚本能调用**活跃的 `direct` 工具**以及**全部 `codemode` / `deferred` 工具**——无论它们是否激活。`codemode` 和 `deferred` 的差别只在于**是否被 codemode 工具在描述里列出来**：

- `codemode` 暴露的工具在描述里列出（并受 `inlineBudget` 预算裁剪）；
- `deferred` 暴露的工具**只在 `ALL_TOOLS` / `searchTools()` 里可达**——正是给"几十上百个 MCP 工具"准备的（第 5 章 §二那个"13,700+ token"的顾虑，落地在这里）。

> **和内置扩展的关系**（第 5 章 §九 的延续）：`codemode` 工具自己就是 `model-only` + `defaultActive: false` + `prepareLoadout`（它用 `prepareLoadout` 把描述动态换成"当前可调用工具清单"）；`tool_search` 也是 `model-only` + `defaultActive: false`，且只搜 `codemode` / `deferred` 暴露的工具；`mcp` 默认把服务器工具注册成 `codemode` 暴露。**第 5 章讲的所有机制，在 Pi 自己的内置扩展里都被用上了。**

## 六、从写一个扩展文件，到它真的跑起来

到现在为止我们讲了扩展"能干什么"和"怎么被调用"。还剩一段旅程要补：**你写下一个 .ts 文件，Pi 怎么找到它、怎么执行它、怎么分发它。**

### 6.1 目录约定：三条发现规则

Pi 从两类位置自动发现扩展（`loader.ts` 的 `discoverAndLoadExtensions`）：

1. **项目本地**：`<cwd>/.pi/extensions/`
2. **全局**：`~/.pi/agent/extensions/`
3. 外加**显式配置的路径**（`-e <path>`、`extensions` 设置、Pi 包里声明的）

在某个目录里，发现规则有三条（`discoverExtensionsInDir` + `resolveExtensionEntries`）：

| 目录里的形态 | 加载什么 |
|------------|---------|
| 直接是 `*.ts` / `*.js` 文件 | 加载该文件 |
| 子目录里有 `index.ts` / `index.js` | 加载 index |
| 子目录里有带 `pi` 字段（`pi.extensions`）的 `package.json` | 加载它声明的那些路径 |

**只发现一层，不递归**——复杂包必须用 `package.json` 显式声明入口。

### 6.2 TS 编译延迟到需要时：Jiti

扩展是 TypeScript 写的，但 Node 不认识 TS。Pi 用 **Jiti**（一个运行时 TS 转译器）在加载时把 `.ts` 直接编译执行（`loader.ts` 的 `loadExtensionModule`）——**你不需要先 `tsc` 出一个 `dist/`**。

而且它有三种解析模式，按运行形态切换：

- **编译后的二进制 / 打包 Node**：用 `virtualModules`（`virtual-modules.ts`），把 `@earendil-works/pi-*` 这些包直接映射到内嵌模块；
- **源码运行（`.ts`）**：同样用 `virtualModules`，外加 `tsconfigPaths: true`；
- **未打包的 Node 构建**：用 `alias`（`getAliases()`），指向 `dist/index.js` 之类的产物。

对写扩展的人，这些差异**完全透明**——你只管 `import { defineTool } from "@earendil-works/pi-coding-agent"`，Jiti 负责把它解析到正确的实现。

### 6.3 热重载：改了就生效

扩展支持热重载——改一个扩展文件，正在跑的会话立即用新版本，不用重启（第 1 章 §3.2 提过，是 Pi 最被低估的一根杠杆）。机制上靠两件事：

- **`reload()`**（`ExtensionCommandContext.reload`，或 `/reload`）：清掉扩展缓存（`clearExtensionCache()`）、重新发现并加载扩展。
- **模块缓存对齐 cwd**：`loadExtensionModule` 用 `extensionCache` 缓存工厂函数，但缓存带一个 `ExtensionCacheToken`（记录 cwd + 代数）——**换了 cwd 或清了缓存，旧缓存立即失效**。`createJitiImpl` 也传了 `moduleCache: false`，确保每次都拿最新代码。

**这条能力催生了一个独特玩法：让编码 Agent 自己改自己的能力。** 你告诉 Pi"给这个扩展再加一个命令"，它改那个 `.ts`，热重载，新命令当场可用。

### 6.4 分发：`pi install` 与 Pi Package

自己写的扩展要给别人用，就打包成 **Pi Package**（第 1 章 §3.2 的第五根杠杆）：

```bash
pi install npm:@foo/pi-tools
pi install git:github.com/user/repo
```

一个 Pi 包可以同时携带扩展、技能、提示词模板、主题（第 1 章 §3.2 讲过这四样）。装完之后，包里的扩展就按 §6.1 的规则参与发现和加载——**"发到 npm，全世界一行命令装上"**，这就是从"自己造"到"社区共享"的那一步。

> 版本与启用：包/扩展是否载入由 `pi config` 和 `extensions` 设置控制；`--no-extensions` 可一次性关掉**全部**扩展（§七 会讲它和内置扩展的关系）。

## 七、内置扩展：`builtin:<name>`

0.99 有一处容易让老用户困惑的变化：**MCP、codemode、tool-search、llama.cpp 这些"产品级能力"，不再是写死在核心里，而是做成了内置扩展**（第 1 章 §3.4 的"立场修正"、第 5 章 §九 也讲过）。本节补齐它的命名与生命周期。

### 7.1 名单

内置扩展列在 `extensions/index.ts` 的 `builtInExtensions`：

```typescript
export const builtInExtensions: InlineExtension[] = [
    { name: "llama.cpp", factory: llamaExtension, builtin: true },
    { name: "codemode", factory: codemodeExtension, replaceable: true, builtin: true },
    { name: "tool-search", factory: toolSearchExtension, replaceable: true, builtin: true },
    { name: "mcp", factory: mcpExtension, replaceable: true, builtin: true },
];
```

| 扩展 | 提供什么 | 暴露方式 |
|------|---------|---------|
| `llama.cpp` | 管理本地 llama.cpp router 的模型（`/llama`），注册一个 provider | 无工具 |
| `codemode` | 让模型写 JS 在 QuickJS 沙箱里 `await tools.read(...)`（嵌套调用） | `model-only`，`defaultActive: false` |
| `tool-search` | `tool_search`：BM25 搜索未声明的工具，命中后加进活跃集合 | `model-only`，`defaultActive: false` |
| `mcp` | 连接 `mcp.json` 与 `pi.registerMcpServer()` 的服务器 | 默认 `codemode`，可配 `deferred` / `direct` / `hidden` |

### 7.2 命名：统一前缀 `builtin:`

内置扩展和内置工具**统一以 `builtin:<name>` 作为路径/来源**。前缀常量 `BUILTIN_PATH_PREFIX = "builtin:"` 定义在 `source-info.ts`，它同时服务内置工具（`builtin:read`）和内置扩展（`builtin:mcp`）。这个前缀会出现在：

- **错误与诊断**（`ExtensionError.extensionPath`）；
- **RPC 的 source info**；
- **bug report**（用户报问题时，来源一眼可辨——"这是内置的"还是"这是某个第三方扩展"）。

判定函数是 `resource-loader.ts` 的 `isBuiltinExtension(input)`（`typeof input !== "function" && input.builtin === true`）。

### 7.3 生命周期：像文件一样加载，但可以被整体关掉

内置扩展被设计成**像一个"扩展文件"那样**参与加载（`InlineExtension` 的类型注释说得很清楚）：默认加载、`pi config` 的 Built-in extensions 区能列出/开关、`-builtin:<name>` 或 `--no-extensions` 可禁用、`-e builtin:<name>` 可显式加载。

三条硬规则必须记清：

1. **`--no-extensions` 会连内置一起关。** 它是"关掉一切扩展"。要保留某个内置扩展，用 `-e builtin:<name>` **单独加载**它。
2. **在项目信任解析之后才加载**，所以内置扩展**无法处理 `project_trust`**（那是加载前就要定的事）。实现上，信任前的引导 pass（`loadProjectTrustExtensions` → `loadCurrentExtensionSet`）会把 `builtin:` 路径过滤掉。
3. **在启动 Extensions 列表里默认隐藏**（加载时 `extension.hidden = true`)。

### 7.4 `replaceable`：内置与第三方"同台竞争"

`codemode` / `tool-search` / `mcp` 三个还带 `replaceable: true`。含义是：**若第三方扩展注册了同名工具/命令/flag（如 `codemode`、`tool_search`、`/mcp`），内置的那个会被替换掉，而不是报命名冲突。** 判定在 `resource-loader.ts` 的 `omitReplacedExtensions`。

这解释了 §5.3 那个"无人处理 MCP 服务器"的场景：一个第三方 MCP 扩展注册 `/mcp`、替换掉内置 MCP 后，它必须自己订阅 `mcp_servers_change` 去连接别人注册的服务器；否则那些注册就没人管，`reportUnhandledMcpServers()` 会把它们报成扩展错误。

> **这为什么和第 1 章的"减法哲学"一致？** 因为内置扩展是"**官方收编**"，不是"焊进内核"。它们以扩展身份存在，因此**可整体禁用、可与第三方替换、可被用户按需开关**。第 1 章 §4.3 那句"不做不可撤销的内建功能，只把验证过的扩展官方化"，在 `builtInExtensions` 这 4 行代码里落地了。

## 八、总结：三个设计 + 一张能力表

回看整章，扩展系统的核心是三个设计，加 0.99 新增的一张能力表。

### 设计一：事件总线暴露关键点

Pi 把 Agent 工作流的**所有关键点**（32 个顶层成员）通过事件总线广播出去，用"事件名 + 返回值协议"这套约定，换取"扩展可以不改源码地介入"。**这是第一层解耦**：Pi 不知道你的需求，但它把决定权交出来了。四种模式（通知/取消/修改/短路）决定了每个点上你能干什么——`tool_call` 能拦、`context` 能改、`session_before_*` 能否决、`turn_end` 能写历史并续跑。

### 设计二：两阶段绑定（throwing stubs + bindCore）

扩展模块的加载顺序不能依赖"核心已就绪"。Pi 的解法是：**注册阶段**给操作型方法填"调用即抛"的桩，**运行阶段**由 `bindCore()` 换成真实实现。`pi` 对象上全是转发器，指向的 runtime 目标被换过一次——扩展代码对此完全无感知。**这是第二层解耦**：加载器与启动流程不再耦死。0.99 的注册型能力（provider / 虚拟模型 / MCP）复用同一套：加载期排队、`bindCore()` flush、绑定后即时生效。

### 设计三：错误隔离 + 最小权限门面

**第三层解耦**是安全：每个 handler 包 `try-catch`，一个扩展崩了只丢自己的改动（`emitToolCall` 例外——它是安全闸门，必须 fail-closed）。同时用三层门面（`ExtensionAPI` / `ExtensionContext` / `ExtensionCommandContext`）把"哪些能力在什么场合可用"编码进类型——`fork` / `switchSession` 只在命令上下文暴露，`sessionManager` 在事件上下文是只读的。

### 0.99 的能力表：拦截 vs 注册

| | 拦截（一直都有） | 注册（0.99 起） |
|---|---|---|
| 入口 | `pi.on(event, handler)` | `pi.registerProvider` / `registerVirtualModel` / `registerMcpServer` / `registerTool` |
| 作用时机 | 对**已经发生**的事做干预 | 往核心里登记**接下来会用到**的资源 |
| 能力 | 拦工具、改上下文、换提示词、写边界 entry | 接入模型 provider、定义虚拟模型、接 MCP 服务器、暴露工具 |
| 共同约束 | 都受"注册阶段 vs 运行阶段"两阶段绑定约束 | 同左 |

**一句话**：0.99 的扩展，从"只能在场边喊话"变成了"能往场上加人"。

### 三个可迁移的思路

1. **用事件总线暴露关键点，而不是给每个点写专门 hook。** 识别工作流的关键节点、emit 统一事件，扩展侧靠"订阅感兴趣的事件"接入——比在核心代码里为每个需求开一个回调扩展性强得多。
2. **throwing stubs + bindCore 分阶段。** 插件加载时核心还没就绪？用"先声明意图（排队/桩）、后执行操作（bind）"这套模式，把加载顺序和初始化顺序解开。
3. **门面分层 + 最小权限。** 给插件不同的门面对象：注册期只给注册能力、事件期只给只读+受控动作、命令期才给特权操作。**永远不要把一个内部大对象直接递给插件。**
